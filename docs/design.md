# ESG Simulator - Technical Design

This document describes the technical design derived from
`docs/specification.md`. It does not define additional business behavior.

## 1. Architecture Overview

The application uses a simplified Hexagonal Architecture:

- **Domain**: `EsgSimulation` and ESG business calculations and rules.
- **Application**: use cases that orchestrate domain operations and persistence
  through ports.
- **Adapters**: REST input adapter and in-memory persistence output adapter.
- **Infrastructure**: Spring Boot wiring and the `ConcurrentHashMap`-based
  repository implementation.

The domain and application core must not depend on HTTP, Spring MVC, or the
persistence implementation.

Runtime flow:

```text
REST adapter -> input port -> application use case -> domain
                                      |
                                      v
                              output persistence port
                                      |
                                      v
                         in-memory ConcurrentHashMap adapter
```

The application uses Java 21, Spring Boot, Maven, REST, JUnit 5, and no
external infrastructure at runtime.

## 2. Proposed Package Structure

```text
src/main/java/<base-package>/
  domain/
    model/
    service/
  application/
    port/
      in/
      out/
    usecase/
  adapter/
    in/
      web/
    out/
      persistence/
  configuration/
```

Suggested responsibilities:

- `domain.model`: `EsgSimulation` and domain values needed by it.
- `domain.service`: ESG calculation logic if it is kept separate from the
  entity while remaining domain-owned.
- `application.usecase`: `CreateEsgSimulation` and `GetEsgSimulation`.
- `application.port.in`: interfaces exposed to input adapters.
- `application.port.out`: persistence interface required by the application.
- `adapter.in.web`: REST controller, request/response DTOs, and HTTP mapping.
- `adapter.out.persistence`: in-memory implementation of the persistence port.
- `configuration`: Spring bean wiring only.

## 3. Domain Model

### EsgSimulation

`EsgSimulation` is the domain entity representing one ESG simulation.

Fields:

| Field | Type | Meaning |
|---|---|---|
| `id` | UUID | Server-generated simulation identifier |
| `portfolioId` | String | Portfolio identifier |
| `carbonEmission` | BigDecimal | Carbon emission indicator |
| `greenInvestmentPercentage` | BigDecimal | Green investment percentage |
| `socialScore` | BigDecimal | Social score |
| `governanceScore` | BigDecimal | Governance score |
| `environmentalScore` | BigDecimal | Calculated environmental score |
| `globalEsgScore` | BigDecimal | Calculated global ESG score |

Domain responsibilities:

- hold the simulation indicators and calculated scores;
- validate the business rules from FR-004;
- calculate the environmental score from `carbonEmission`;
- calculate `globalEsgScore` using the specified weights;
- round `globalEsgScore` to two decimal places using `RoundingMode.HALF_UP`;
- keep `greenInvestmentPercentage` in the simulation without using it in the
  global score calculation.

The UUID is generated by the application/domain creation flow on the server;
it is not accepted from the POST request.

## 4. Application Layer

### CreateEsgSimulation

The use case:

1. receives the creation input from an input port;
2. creates a domain simulation with a server-generated UUID;
3. applies domain validation and ESG calculations;
4. saves the resulting simulation through the persistence output port;
5. returns the created simulation to the REST adapter.

### GetEsgSimulation

The use case:

1. receives a simulation identifier;
2. loads the simulation through the persistence output port;
3. returns it when found;
4. raises an application-level not-found condition when it does not exist.

The application layer does not know whether persistence is implemented with a
map, JPA, or another adapter.

## 5. Ports

### Input ports

- `CreateEsgSimulation` input port: accepts the creation data and returns the
  created simulation.
- `GetEsgSimulation` input port: accepts a simulation UUID and returns the
  corresponding simulation or a not-found result/error.

The REST adapter depends on these interfaces rather than on use-case
implementations.

### Output/persistence port

A simulation persistence port must provide operations to:

- save a simulation;
- find a simulation by UUID.

The port uses domain/application concepts and contains no `ConcurrentHashMap`,
Spring Data, or database-specific types.

## 6. Adapters

### REST adapter

The REST adapter exposes:

- `POST /api/v1/esg/simulations`;
- `GET /api/v1/esg/simulations/{id}`.

It converts JSON to a request DTO, invokes an input port, converts the domain
result to a response DTO, and maps application/domain errors to HTTP statuses.
It must not contain ESG calculations or persistence logic.

### In-memory persistence adapter

The in-memory adapter implements the persistence output port using a
`ConcurrentHashMap<UUID, EsgSimulation>` (or an equivalent map whose key is the
UUID). It stores and retrieves simulations for the lifetime of the application.

It has no business calculation responsibilities and does not require a
 database, Docker, PostgreSQL, or any external service.

## 7. API Contract

### POST /api/v1/esg/simulations

Request DTO fields:

- `portfolioId`: text value;
- `carbonEmission`: decimal numeric value;
- `greenInvestmentPercentage`: decimal numeric value;
- `socialScore`: decimal numeric value;
- `governanceScore`: decimal numeric value.

The request does not contain `id`, `environmentalScore`, or
`globalEsgScore`; these are generated or calculated by the server.

A successful response has HTTP 201 and contains a response DTO with:

- server-generated `id`;
- submitted input indicators;
- calculated `environmentalScore`;
- calculated `globalEsgScore`.

### GET /api/v1/esg/simulations/{id}

The path contains the simulation UUID. A successful response has HTTP 200 and
returns the same response DTO shape as the POST response.

### HTTP status codes

- `201 Created`: simulation successfully created;
- `200 OK`: simulation successfully retrieved;
- `400 Bad Request`: invalid request or invalid business input;
- `404 Not Found`: no simulation exists for the requested identifier.

The exact JSON error body is not defined by the specification.

## 8. Validation Strategy

### Technical/API validation

The REST boundary validates request shape and conversion, including:

- malformed JSON;
- missing mandatory fields;
- values that cannot be read as decimal numeric values;
- an invalid path identifier representation, if it cannot be converted to a
  UUID.

### Business/domain validation

The domain validates:

- `portfolioId` is not null, empty, or whitespace-only;
- `carbonEmission` is not less than zero;
- `greenInvestmentPercentage` is between 0 and 100;
- `socialScore` is between 0 and 100;
- `governanceScore` is between 0 and 100.

`greenInvestmentPercentage` remains mandatory and is stored, but is not used
in the global score calculation.

### HTTP 400 mapping

Technical validation failures and business validation failures are translated
by the REST error-handling boundary to HTTP 400. Validation must happen before
persistence.

## 9. ESG Calculation Rules

### Environmental score

Using `BigDecimal` comparisons:

- `carbonEmission <= 100` -> `environmentalScore = 100`;
- `carbonEmission > 100` and `carbonEmission <= 500` ->
  `environmentalScore = 70`;
- `carbonEmission > 500` -> `environmentalScore = 40`.

### Global ESG score

`greenInvestmentPercentage` is excluded from this calculation.

```text
0.40 * environmentalScore
+ 0.30 * socialScore
+ 0.30 * governanceScore
```

The calculation uses `BigDecimal`. The result is rounded to exactly two
 decimal places with `RoundingMode.HALF_UP` and must be between 0 and 100.

## 10. Error Handling

### Validation errors

Invalid request shape or invalid business input produces HTTP 400. The
controller boundary owns the HTTP mapping; the domain owns the business rules.

### Simulation not found

When the output port cannot find the requested UUID, the application signals a
not-found condition. The REST adapter maps it to HTTP 404.

No other error behavior is added by this design because it is not specified.

## 11. Test Strategy

### Unit tests

Domain unit tests cover:

- environmental score at, below, and above thresholds 100 and 500;
- validation boundaries and invalid values;
- global score weighting;
- exclusion of `greenInvestmentPercentage`;
- two-decimal `HALF_UP` rounding;
- the global score range.

### Application/use-case tests

Use-case tests use a fake persistence adapter or Mockito to verify:

- valid creation calculates and saves a simulation;
- the identifier is generated server-side;
- invalid domain input is not saved;
- retrieval returns an existing simulation;
- retrieval reports not found for an unknown UUID.

### REST/API tests

Spring MVC/API tests verify:

- valid POST returns 201 and calculated fields;
- invalid inputs return 400;
- valid GET returns 200;
- unknown UUID returns 404;
- request and response field mapping;
- persistence is not required to be external.

Tests use JUnit 5. Mockito may be used for application-port collaborators where
it makes the test clearer.

## 12. Traceability

| Requirement | Design components |
|---|---|
| FR-001 Create a simulation | `CreateEsgSimulation`, `EsgSimulation`, REST POST adapter, persistence output port, in-memory adapter |
| FR-002 Environmental score | `EsgSimulation` domain calculation using the three specified thresholds |
| FR-003 Global ESG score | `EsgSimulation` domain calculation using 40/30/30 weights, BigDecimal, and HALF_UP rounding |
| FR-004 Input validation | REST request validation, domain validation, and HTTP 400 error mapping |
| FR-005 Retrieve a simulation | `GetEsgSimulation`, persistence output port, REST GET adapter, and HTTP 404 mapping |

## 13. Future Evolution

A future `JpaSimulationRepository` can implement the same persistence output
port as the in-memory adapter. Its database entities and mapping code would
remain inside the infrastructure/adapter layer.

Replacing the adapter would require changing Spring wiring and adding the
PostgreSQL/JPA infrastructure only. The domain model, ESG rules, use cases,
input ports, and application contracts would remain unchanged.

PostgreSQL and JPA are not part of the current implementation; this section
only describes the replacement boundary requested for future evolution.

## Remaining Ambiguities

The following details are not defined by the specification and therefore are
left open:

- the exact JSON error-body structure;
- the exact JSON representation of a UUID, although the identifier is a UUID;
- the maximum precision and scale accepted for `BigDecimal` input values;
- whether `null` numeric values must be reported specifically as missing fields
  or as generic invalid requests;
- whether `carbonEmission` must be explicitly rejected when absent or null,
  even though it is listed as a required simulation field and numeric input.
